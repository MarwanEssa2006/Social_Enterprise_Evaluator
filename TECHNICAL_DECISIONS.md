# Technical Decisions

Social Enterprise Evaluation Platform — implementation decisions made under D-40 (autonomous implementation authority).
Each decision is reversible unless stated. Sources accessed 2026-11-20.

| ID | Decision | Choice | Why | Alternatives rejected |
|---|---|---|---|---|
| TD-01 | Application shape | **One Next.js 16 application (App Router, TypeScript)** containing UI, server actions, and route handlers, in `platform/`. | One deployable unit fits the scale (single team, modest traffic); server-side rendering keeps secrets and scoring on the server. No microservices. | Separate SPA + API server (two deployables, duplicated types); microservices (over-engineering). |
| TD-02 | Database | **SQLite through Node's built-in `node:sqlite`**, plain SQL migrations, thin repository layer. File: `platform/data/app.db`. | No native build step on Windows (Node 26 ships SQLite); transactional, file-based, easy to back up; enough for pilot scale. Repository layer isolates SQL so PostgreSQL can replace it for production. | Prisma (engine downloads, heavier); better-sqlite3 (native compile risk on Node 26/Windows); PostgreSQL now (needs a server; premature for pilot). |
| TD-03 | Authentication | **Own email + password auth**: `scrypt` (node:crypto) password hashing, random session tokens stored **hashed** in DB, `HttpOnly` + `SameSite=Lax` (+ `Secure` in production) cookie, 30-day expiry, logout deletes session. | Few dependencies, fully server-side, no third-party identity provider needed for a pilot. | Auth.js (extra config surface for credentials only); hosted auth (external dependency, cost). |
| TD-04 | Authorisation | Every project query is filtered by `owner_id = current user`; other users' projects return 404 (no existence leak). | Prevents horizontal access; tested. | Role system (not needed yet; FDD-01). |
| TD-05 | Validation | **Zod** on every server action / route input. | Single schema source; also used for AI output schemas. | Manual checks. |
| TD-06 | UI | **Tailwind CSS v4** with small in-house components; system font stack with Arabic coverage (Segoe UI / Tahoma / Noto). | Lightweight, consistent, no runtime UI library; no network font download at build. | Component kits with heavy runtime; Google Fonts (network at build). |
| TD-07 | Language | **Arabic default, English available**; `dir="rtl"` for Arabic; cookie-based switch. **Approved questions and options are always displayed in their exact Arabic wording** (D-19); English UI shows an English helper label only for navigation. | Template, question bank, and target context are Arabic (Egypt references in template notes). Translating approved questions would be rewriting them. | English default; translated questions. |
| TD-08 | Scoring Engine | Pure, deterministic TypeScript module `src/lib/scoring/` implementing `EVALUATION_FRAMEWORK.md` readings and `SCORING_SPECIFICATION.md` M1.0. No I/O, no AI. Versioned by `METHODOLOGY_VERSION = "M1.0"`. | Testable in isolation (NFR-14); deterministic (D-34..D-37). | Rules in DB/config now (unneeded complexity for one version). |
| TD-09 | Question bank source | `src/lib/questions/bank.ts` generated from the verified bank text (machine-checked against `EVALUATION_FRAMEWORK.md`). IDs: `C{n}-Q{m}`, options `C{n}-Q{m}-O{k}` in approved order; LM follow-up `C1-EF`. | IDs are needed for recommendations and AI grounding without touching wording. | Hand-typed copy (error-prone). |
| TD-10 | AI integration | Provider interface `AiProvider.generateStructured()` with **GeminiProvider** (`@google/genai`, server only, `GEMINI_API_KEY` env) and **MockProvider** (default when no key or `AI_MODE=mock`). Structured output via `responseMimeType: application/json` + `responseJsonSchema` (from Zod). | Modular provider (D-38); mock mode for safe testing (D-39). Source: https://ai.google.dev/gemini-api/docs/generate-content/structured-output | Direct REST calls scattered in code. |
| TD-11 | Gemini model | Configurable `GEMINI_MODEL`, default `gemini-2.5-flash`; low temperature (0.2); max output tokens capped per call. | Stable, low-cost model; configurable because model IDs change. Confirm against https://ai.google.dev/gemini-api/docs/models before go-live. | Hard-coded model. |
| TD-12 | AI call pattern | **One call per criterion** (8 calls, run with concurrency 2), each with a grounded fact sheet; no summary call (overall text is assembled deterministically). | Independent analysis per criterion; small prompts; partial failures fall back per criterion. | One giant call (single failure point, weaker grounding). |
| TD-13 | AI errors | Retry only 429 / 408 / 5xx / timeouts, max 3 attempts, exponential backoff with jitter, 30 s timeout per call; no retry on 400/401/403. Invalid JSON or failed validation → one corrective retry → deterministic fallback text. Scores never depend on AI. | Follows Google troubleshooting guidance: https://ai.google.dev/gemini-api/docs/troubleshooting | Unlimited retries. |
| TD-14 | AI grounding | Fact sheet items have IDs; every AI statement must cite IDs; validator rejects unknown IDs, any number not present in the fact sheet, any score-like text, and recommendations not selected by the library. | Prevents invented facts and score talk (D-20, Phase 4 rules). | Free-form prompts with trust. |
| TD-15 | Data sent to AI | Only answer codes/text, project context (country, area, model), evidence metadata and descriptions, scoring results. **Never** user email, names of people, or uploaded file contents. Project name replaced by "the project". | Data minimisation (D-39). | Sending files. |
| TD-16 | Gemini data terms | Live Gemini use only with a **paid (billing-linked) project** and approved data handling; unpaid quota content may be used by Google to improve products and reviewed by humans. Sources: https://ai.google.dev/gemini-api/terms | Owner rule D-39; OPEN-19/20 remain owner decisions. | Free tier with real data. |
| TD-17 | Recommendation Library | Code-defined library (`src/lib/recommendations/library.ts`), bilingual (ar/en), entries derived from the approved trigger tables (framework §6.8–13.8); deterministic selection and priority; AI only personalises wording. | Maintainable, reviewable, not dependent on AI (Phase 4 rule). | AI-generated recommendations. |
| TD-18 | Recommendation status | User-facing statuses **Not Started / In Progress / Completed** (owner Phase 4 brief). Status never changes scores (D-14). Implementation evidence notes/files can be attached. | Matches owner instruction; supersedes the proposed 6-state list in `PRODUCT_DEFINITION.md` §7.3. | — |
| TD-19 | Versioning | Assessment rows are insert-only (no UPDATE/DELETE statements exist for them); each stores input snapshot, methodology version, results, AI output. Comparisons re-score the older snapshot under the newer methodology to separate methodology changes from project changes (spec §8). | D-12, D-32. | Mutable results. |
| TD-20 | PDF | **HTML → PDF with headless Chromium (Playwright)**. | Correct Arabic shaping and RTL, which JS PDF libraries handle poorly; Chromium is also used for E2E tests. | @react-pdf / pdfmake (Arabic shaping problems). |
| TD-21 | Excel | **Populate the original template by editing only the eight response cells in the sheet XML (JSZip)**; every other part of the file is copied unchanged. Verified by re-reading with ExcelJS in tests. | Maximum fidelity to the template (D-10); no re-creation. | Re-writing the workbook with a library (may drop notes/formatting). |
| TD-22 | Excel mapping (OPEN-27, decided under D-40) | Each criterion's response area (C5, F5, I5, L5, C14, F14, I14, L14) receives: Commercial score, Social score, Evidence Confidence, top recommendation. No other cells changed. | Uses the template's own response areas only. | Adding sheets/cells (changes structure). |
| TD-23 | File uploads | Evidence files: max 5 MB, allow-list (pdf, png, jpg, jpeg, xlsx, docx, csv, txt), stored outside `public/` with random names, served only through an authorised route with `Content-Disposition: attachment`. Not sent to AI. | Safe upload handling. | Public folder storage. |
| TD-24 | Grants flag | Project information includes "grants or donations currently cover part of operating costs" (yes/no). Used only to raise the Grant-dependent flag defined in the framework; never treated as revenue. | The framework needs a deterministic trigger for this flag. | Inferring from free text. |
| TD-25 | Testing | **Vitest** (unit, integration, DB with temporary SQLite files, AI validator, exports) and **Playwright** (end-to-end, responsive checks). | Fast, TypeScript-native; Playwright shared with PDF. | Jest. |
| TD-26 | Deployment (target) | Single Node server (`next start`) behind HTTPS reverse proxy; SQLite file on persistent disk with daily backup for pilot; migrate to PostgreSQL before multi-instance scaling. | Simple and cheap for a pilot. | Serverless (SQLite file storage incompatible). |
| TD-27 | Next.js caching model | `cacheComponents: false` (documented previous model). | Every page reads the user session; Cache Components would require Suspense boundaries around all session reads with no benefit for per-user pages. Source: `node_modules/next/dist/docs/01-app/02-guides/caching-without-cache-components.md`. | Cache Components (complexity without benefit here). |
| TD-28 | Current path for language switch | `src/proxy.ts` (Next 16 "Proxy", formerly Middleware) sets `x-pathname`. Not used for authorisation. | Lets the language switch return to the same page. | Client-side switch (needs client JS on every page). |
| TD-29 | Script runner | `tsx` (dev dependency) for the seed script. | Runs TypeScript with path resolution and the `react-server` condition. | Node type stripping (no extensionless imports). |
| TD-30 | Excel cell content | One line per response cell, parts separated by " \| ". | Template cells have no text wrapping; changing formatting is not allowed (D-10). | Enabling wrap (modifies template formatting). |
| TD-31 | Phase 4 documentation | The separate Phase 4 design documents requested earlier were superseded by the instruction to implement; the AI design is consolidated in `ARCHITECTURE.md` §6 and the code. | Avoids parallel documents drifting from the implementation. | Writing five separate design documents. |
| TD-32 | Evidence guidance (OPEN-38) | Implemented as a structured evidence-type list per criterion and dimension, plus a short hint, rather than free-text prompts. Exact wording of the §16.3 draft prompts remains for owner review. | Structured types map directly to evidence classes (confidence rules). | Free-text prompts only. |
